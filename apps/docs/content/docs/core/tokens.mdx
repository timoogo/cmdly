---
title: "Tokens"
description: "Recognize prefixed and prefix-less tokens in the input, validate them, and hand them to commands."
---

Tokens are pieces of the query such as `@alice`, `#42` or `bob@example.com`. Cmdly recognizes and validates them; **it never filters commands or blocks execution because of them**. The rest of the query (`snapshot.text`) still drives search, and your commands decide what tokens mean. Tokens are unrelated to command tags.

```ts
import { createCommandEngine, defineTokenType, type Command } from '@cmdly/core';

const user = defineTokenType({
  id: 'user',
  prefix: '@',
  match: async (login, { signal }) => {
    const response = await fetch(`/api/users/${encodeURIComponent(login)}`, { signal });
    if (!response.ok) return { valid: false, message: `Unknown user ${login}` };
    return { valid: true, data: (await response.json()) as { id: string; name: string } };
  },
});

const assign: Command = {
  id: 'assign',
  label: 'Assign',
  run: async (_answers, context) => {
    const tokens = (await context?.settleTokens?.()) ?? [];
    if (tokens.some(token => token.type === 'user' && token.status !== 'valid')) throw new Error('Fix the users first');
  },
};

const engine = createCommandEngine({ commands: [assign], tokens: { types: [user] } });
engine.setQuery('assign @alice');
// engine.getSnapshot().text   → 'assign' (drives search)
// engine.getSnapshot().tokens → [{ type: 'user', value: 'alice', status: 'pending', … }]
```

## Token types

| Field | Meaning |
| --- | --- |
| `id` | Unique within its scope. |
| `prefixMode` | `'required'` (default) or `'none'`. |
| `prefix` | Required in `'required'` mode: one or more non-whitespace characters, recognized at the start of a word. |
| `detect` | Required in `'none'` mode: a `RegExp` or `(word) => boolean` tested on whole words. It only detects; validation belongs to `match` or `values`. |
| `values` | Optional value registry `{ value, label?, data? }[]`, matched case-insensitively. |
| `match` | Custom validator `(value, { signal, type })`, synchronous or asynchronous. Mutually exclusive with `values`. |

### `detect` and RegExp flags

A `RegExp` is tested against each whole word, always from the start of the word. Cmdly works on a private copy: your instance and its `lastIndex` are never modified. Flags keep their native meaning (`i`, `u`, `s`, `m`…), with two precisions:

- `g` has no effect: no state is carried from one word, keystroke or engine to the next.
- `y` (sticky) requires the match to start at the first character of the word, as if the pattern began with `^`.

Without `^…$`, the pattern may match part of the word (`/x\d/` accepts `ax1`). A `detect` function is called as is; any state it keeps is yours.

Without `values` or `match`, any non-empty value is valid. `defineTokenType()` infers the type of `data`. Invalid definitions throw `CmdlyError` with code `INVALID_TOKEN_TYPE`.

### `match` results

`match` returns a `boolean`, `{ valid: true, data }` or `{ valid: false, message? }`, possibly through a promise. A thrown error or a rejection gives the `error` status; any other value gives `error` with code `INVALID_TOKEN_MATCH`. An empty value (a bare prefix) is `invalid` and `match` is not called.

Asynchronous validations are `pending` first. When a token changes or disappears, when the palette closes, or when the engine is destroyed, its `AbortSignal` is aborted and late results are ignored. An unchanged token keeps its state across keystrokes.

## Statuses

`pending`, `valid`, `invalid`, `error`, or `ambiguous`. Each `Token` carries `id`, `type`, `candidates`, `prefix`, `value`, `raw`, `start`, `end`, `status`, and optionally `data`, `message`, `error` and `step` (the step where it was typed).

`id` is stable for the token's lifetime and usable as a React key. Identical tokens (same scope, type and value) are tracked per occurrence: in `@a @a`, deleting the first `@a` leaves one token that keeps the first id, and the second occurrence's validation is cancelled. The result is the same since the value is the same.

## Scopes and collisions

Global types come from `tokens.types` (engine option or `CommandPalette` prop). Commands and steps can declare local `tokens`: in a step, the step types come first, then the command chain (innermost first), then global types. A group command's types are active in its submenu.

For each whitespace-separated word, resolution is deterministic:

1. The longest active prefix wins, whatever its scope.
2. Prefix-less types are tried only when no prefix matches.
3. Among equal prefixes (or prefix-less types), the innermost scope wins: local types shadow global ones.
4. Several types left in the same scope go to `tokens.resolve({ prefix, value, candidates, scope })`. Returning one of the candidate ids selects it; anything else leaves the token `ambiguous`. Cmdly never picks arbitrarily.

```ts
const tokens = {
  types: [issue, label], // both use '#'
  resolve: ({ value }) => (/^\d+$/.test(value) ? 'issue' : 'label'),
};
```

## Dynamic registration

`engine.tokens.register(type)` adds or replaces a global type and returns a disposer; `engine.tokens.unregister(id)` removes it; `engine.tokens.setValues(id, values)` replaces a value registry (not available for `match` types). `engine.setOptions({ tokens })` replaces all global types and the resolver. Local types follow their commands: register the command again to change them. Prefer `match` over `values` when data already lives elsewhere; Cmdly never requires duplicating it.

Replacing a type cancels the validation of current tokens of that type and validates them again with the new definition; late results of the old one are ignored. Re-applying **equivalent** definitions (same id, prefix or `detect`, same `match` function, equal `values`) changes nothing: no revalidation, no new snapshot. This is what makes `tokens={{ types: [...] }}` safe in React, as long as `match` functions are stable: declare them outside the component (or memoize them), otherwise each render is a real change. Changing only `resolve` re-resolves current tokens.

Captured tokens are not affected by later changes: they finish validating with the definition they were captured with, even if the type is replaced or unregistered.

## Captured tokens and execution

Selecting an item captures the tokens of the current query along the workflow path, like answers. Going back leaves the tokens captured by the steps you leave, and the query of a step you return to is empty, as before. Going forward (between steps, into submenus, or back to the final step) restores exactly the tokens captured the first time. Navigation never cancels captured validations.

`run` receives `{ tokens, settleTokens, signal }` as its second argument (inside the `context` object for registry commands, which also reaches `options` and `when`). These fields are present only when tokens are configured, so existing commands keep receiving exactly what they did before.

- `settleTokens()` resolves once no captured token is pending, and **rejects with an `AbortError`** once the palette is closed or destroyed, even if every token had already settled.
- `signal` is aborted when the palette is closed or destroyed, never by navigation. Pass it to your own requests.
- Whether to wait, refuse or proceed is up to the command. Cmdly ignores the result of a run that outlives its session, but **it cannot undo side effects**: check `signal` (or let `settleTokens()` reject) before acting.

## Feedback

`snapshot.tokenFeedback` aggregates the current and captured tokens independently of any rendering: `status` (`error` > `ambiguous` > `invalid` > `pending` > `valid`, or `idle`), `pending` and `issues`. Empty tokens are ignored. `snapshot.tokensEnabled` tells whether tokens can be recognized at the current position or were captured.

`CommandPalette` renders it globally through `tokenFeedback`:

- `'banner'` (default): lists issues and the validation in progress, linked to the input with `aria-describedby`. Each issue is announced once per status in a polite live region. The announcement is cleared when the issue it describes disappears, and an identical follow-up message is announced again.
- `'loader'`: shows a global indicator and sets `aria-busy` on the list while tokens are pending; every validation episode is announced, and the announcement is cleared when it ends.
- `'none'`: renders nothing; read `state.tokenFeedback` from `useCommandEngine`.
- A component: receives `{ feedback, tokens }` (including while `idle`, so it can host its own live region) and owns its accessibility.

The feedback stays visible during the final confirmation step. Live regions and custom components are mounted as soon as tokens become possible (a `tokens` prop or local types in the current scope), before the first message. Nothing is rendered when no token type is configured. Built-in texts are in English; use `message` in `match` results or a custom component to localize them.

## Limitations

No value autocompletion, no quoted values or values containing spaces, prefixes are recognized only at the start of a word, `detect` is synchronous, there is no built-in debounce (use `signal`), no per-type feedback, built-in feedback texts are English only, local types cannot be registered independently of their command yet, captured tokens are not revalidated when their type changes, and step option loaders are neither reloaded when tokens change nor aborted.
